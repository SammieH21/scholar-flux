## [0.6.1] - 07/14/2026
### Security

**Package Dependencies**:
- **Cryptography Dependency Update**: Updated the minimum supported `cryptography` version from v48.0.0 to v48.0.1 to address a high-severity OpenSSL Denial of Service vulnerability (`CVE-2026-34180`) resulting from the out-of-bounds processing of a malicious ASN.1 structure.
- **PyMongo Dependency Update**: Updated the minimum supported `pymongo` version from v4.0.0 to v4.6.3 to address an out-of-bounds read vulnerability in the `bson` module (`CVE-2024-5629`) where malformed BSON from a MongoDB server could expose application memory in exception messages. This update mitigates potential exposure when retrieving responses via the MongoDB session/response cache.
- **PyYAML Dependency Update**: Updated the minimum supported `pyyaml` version from v5.0.0 to v6.0.2 to address arbitrary code execution vulnerabilities in non-safe loaders among earlier versions (`CVE-2019-20477`, `CVE-2020-1747`, `CVE-2020-14343`). While ScholarFlux, which parses `application/yaml` response content via `yaml.safe_load()` exclusively, was unaffected, this version increase ensures that all installations include relevant patches and have Python 3.10+ wheel support.
- **Redis Dependency Update**: Updated the minimum supported `redis` version from v4.0.0 to v4.5.4 to address race conditions in the async client that could leak response data across clients (`CVE-2023-28858` and its incomplete-fix follow-up, `CVE-2023-28859`). Although ScholarFlux exclusively uses the synchronous `redis.Redis` client and was unaffected, this update ensures that `redis` installations via `scholar-flux[database]` include the required security patch.
- **Starlette Transitive Dependency Update**: Updated the `docs` dependency group to explicitly define `starlette>=1.3.1` as the minimum package dependency, addressing `CVE-2026-54282` (host spoofing/BADHOST path traversal) and `CVE-2026-54283` (DoS vulnerability via request.form() limits) to ensure that the installation of `sphinx-autobuild` does not introduce a vulnerable version of the `starlette` transitive dependency.


## [0.6.0] - 05/31/2026
**Note**: While the changes to the `SearchAPI` are substantial, user-facing changes are backward compatible with previous versions, mainly hardening security, improving API consistency, and introducing dedicated auth functionality. Existing codebases and workflows will not require modification to benefit from this update aside from special cases defined below:

**Migration**:
- **SearchAPI**: When directly initializing new `SearchAPI`, the majority of parameters, albeit for niche use cases, are available for convenience. With logical delimiters between positional and keyword parameters for readability, calls should be specific: specify parameters directly through keyword arguments (e.g., `api = SearchAPI(query='your-query', provider_name='plos', user_agent="your user agent (mailto:your@email.address.com)", timeout=30)`).
- **ConfigLoader.write_key**: While an uncommon use case (`ConfigLoader.write_config` is the front-facing method), ensure that method calls specify `key` and `value` either as positional parameters or with the new parameter names, `key`, and `value`. When writing to the environment with a nondefault .env file, specify the keyword directly: `config_settings.write_key("SCHOLAR_FLUX_DEFAULT_USER_AGENT", "scholar-flux-v0.6.0 (mailto:***)", env_path="path/to/your/.env", create=True)`.
- **MongoDBStorage.DEFAULT_CONFIG Class Attribute**: Ensure that, to access parameter defaults, you either use `MongoDBStorage.get(...)` (the `db` and `collection` keys are now default `DEFAULT_DATABASE` and `DEFAULT_COLLECTION` class attributes, respectively) or use `MongoDBStorage.get_default_config()` to access both connection parameters and database/collection specifications created after the resolution of configuration settings.
- **API keys vs. Auth Settings**: Either declare the `SearchAPI` `api_key` on instantiation, specify the key using the correct environment variable (`e.g., CROSSREF_API_KEY, CORE_API_KEY, SPRINGER_NATURE_API_KEY`) — letting the `SearchAPIConfig` read and mask the key, or migrate to using `auth` per request instead - the API key injection step is generally handled for you when an environment variable is needed or the configured environment variable for a provider has a corresponding value.

### Security

**Package Dependencies**:
- **idna Transitive Dependency Update**: Updated idna to address `CVE-2024-7347`, which details an SSL/TLS certificate validation issue on IDNA 2008 normalization.
- **requests, urllib3, and requests-cache Dependency Updates**: Updated `requests` (2.33.0 → 2.34.2), `urllib3` (2.6.3 → 2.7.0), and `requests-cache` (1.2.0 → 1.3.2) minimum version requirements to the latest recommended, secure, backward-compatible versions supported by `ScholarFlux` and audited by the `Safety CLI`.
- **pydantic, sqlalchemy, beautifulsoup4 Updates**: Updated `pydantic` (2.10.6 → 2.13.4), `sqlalchemy` (2.0.0 → 2.0.50), and `beautifulsoup4` (4.9.0 → 4.14.3) minimum version requirements to the latest recommended secure versions according to Safety CLI. These updates also maintain backward compatibility, keeping major version numbers unchanged and Python 3.10-3.14 support unaffected.
- **cryptography Dependency Update**: Updated the minimum supported `cryptography` version from 46.0.7 to 48.0.0. This version of the `cryptography` package is the latest secure release, as audited by `Safety CLI`, and retains backward compatibility with existing `ScholarFlux` functionality.
- **xmltodict Dependency Update**: Updated the minimum supported `xmltodict` version (0.12.0 → 0.15.1) to resolve dependency vulnerability issues identified among earlier versions as audited by `Safety CLI`. The updated `xmltodict` dependency maintains backward compatibility with existing `ScholarFlux` functionality.

**Session Cache & Authentication**:
- **Encryption Pipeline Environment Default**: Refactored the `CachedSessionManager` to initialize with a valid `EncryptionPipelineFactory` when `SCHOLAR_FLUX_USE_SESSION_CACHE_ENCRYPTION` is enabled. At runtime, the environment variable coerces truthy values ('1', 'true', True, 'T') to True and ('0', 'false', False, 'F') to False. When a serializer isn't already specified, and a valid `Fernet` key (32-byte URL-safe base64 key) is stored via the `SCHOLAR_FLUX_CACHE_SECRET_KEY` environment variable, the session cache will attempt to initialize with encryption.
- **CachedSessionManager Serializer Initialization**: A convenience `CachedSessionManager.get_serializer` class method enables the creation of an encryption pipeline serializer if it is not specified. This method uses error handling via the `raise_on_error` keyword parameter to gracefully handle edge cases when enabled. If serializer initialization fails due to a missing encryption dependency or invalid secret key, the error will be logged when `raise_on_error=False` and re-raised after logging when `raise_on_error=True`.
- **Session AuthAPIKeyHeader & AuthAPIKeyParameter Integration**: `SearchAPI` API key preparation now introduces `AuthAPIKeyHeader` and `AuthAPIKeyParameter` for handling special cases requiring customized logic for API key or token-based authentication. The `SearchAPI.build_auth` method integrates the authentication handling logic via the `auth=` requests parameter to dynamically modify `requests.PreparedRequest` structures and optionally add API keys via headers for specific provider configurations.
- **Optional Encryption Parameter**: `CachedSessionManager.__init__()` and `CachedSessionManager.with_session()` each add a `use_encryption: Optional[bool]` parameter for overriding the `SCHOLAR_FLUX_USE_SESSION_CACHE_ENCRYPTION` environment variable default to enable per-session encryption configuration. By default, this parameter is `None`, meaning that encryption utilization is delegated to the existing environment variable defaults.
- **Redis & MongoDB Environment Authentication**: The session and response cache backends now support the use of `SCHOLAR_FLUX_MONGODB_USERNAME`, `SCHOLAR_FLUX_MONGODB_PASSWORD`, `SCHOLAR_FLUX_REDIS_USERNAME`, and `SCHOLAR_FLUX_REDIS_PASSWORD` environment variables for opt-in database authentication. These settings are included in the output of `MongoDBStorage.get_default_config()` and `RedisStorage.get_default_config()` only when their respective values are explicitly specified within the environment and are prefixed with `SCHOLAR_FLUX_*`. Any assigned secret strings are unmasked via `SecretUtils.unmask_secret()` at the time of connection.
- **MongoDB Session Cache Building Update**: Introduced a `CachedSessionConfig.build_cache()` method for building a `requests_cache.BaseCache` `backend` subclass when special cases require direct instantiation. As of v0.6.0, this only applies to `MongoDB` to handle a potential authentication issue beforehand. The `requests-cache` backend as of `v1.3.2` removes `username` and `password` keyword parameters before cache instantiation when they don't match a predefined set of valid keywords, potentially resulting in `unauthorized` errors on connection. The `configure_session` unconditionally calls `build_cache` which operates and returns a session config only when needed to build the `requests_cache.MongoCache` from a newly initialized client via `MongoDBStorage.initialize_client` while removing keyword parameters via a modified copy of the `CachedSessionConfig` ahead of time. When `build_cache` doesn't apply, a copy of the current config is returned and used to configure a new session instead.

**Data Masking**:
- **SensitiveDataMasker Pattern Update**: The `SensitiveDataMasker` now masks API keys and tokens that match common schemas containing the `sk-` (OpenAI) or `sk-ant-` (Anthropic) prefix. This addition is intended for downstream embedding services and retrieval augmented generation integrations requiring retrieved and processed records via ScholarFlux (e.g., the soon-to-be-released ScholarFlux MCP server).
- **SecretUtils.unmask_parameters**: `SecretUtils` now implements a `SecretUtils.unmask_parameters` helper method for efficiently unmasking a dictionary of secrets. This addition is helpful for scenarios where an arbitrary number of keyword parameters should remain masked until their underlying values are used (e.g., cache initialization, API configuration parameters, persisting settings to .env files, etc.).
- **SettingsDict Addition**: Introduced `SettingsDict` for auto-masking environment variable-value pairs when printing the dictionary to the console. The `scholar_flux.utils.settings_utils.SettingsDict` is a backward-compatible `UserDict[str, Any]` subclass that automatically masks sensitive data based on the package-level masking configuration when displayed in the console. For tricky cases such as when a generally nonsensitive environment variable or cache configuration setting holds obviously sensitive data, this modification prevents accidental exposure (e.g., `{"SCHOLAR_FLUX_USER_AGENT": "[Your Name] (mailto:***)"}`).
- **SettingsDict Integration**: Implemented the `SettingsDict` for auto-masking cache, API, and configuration settings when printed to the console. This refactor spans the `ConfigLoader`, `SearchAPIConfig`, `CachedSessionManager`, `MongoDBStorage`, `RedisStorage`, and `SQLAlchemyStorage` classes, each of which guards potentially sensitive parameters when viewed in IPython, Jupyter Notebook, or similar environments. This implementation is used as a drop-in replacement for configuration settings of type `dict[str, Any]` with the caveat that it is a `UserDict` subclass rather than a `dict`.

**Redis & MongoDB Response Cache Initialization**:
- **MongoDBStorage Initialization**: Refactored the `MongoDBStorage` initialization to use a dict comprehension with `SecretUtils.unmask_secret()` to unpack and forward all parameters within its config dictionary on `MongoClient` initialization via `MongoDBStorage.initialize_client()`, including keyword parameters and excluding non-connection keys (database, `db`, `collection`, `ttl`). This replaces the explicit usage of `host=self.config['host']` and `port=self.config['port']` for `MongoClient` initialization. A username and password are only provided during MongoDB client initialization when either is provided via keyword parameters or read from the `SCHOLAR_FLUX_MONGODB_USERNAME` or `SCHOLAR_FLUX_MONGODB_PASSWORD` environment variables via `config_settings`.
- **RedisStorage Initialization**: Refactored the `RedisStorage` to use `SecretUtils.unmask_parameters()` to unmask secrets and unpack keyword parameters to initialize the `redis.Redis` client via `RedisStorage.initialize_client`. Authentication parameters are only added when explicitly defined by the user, either in the initialization of the `RedisStorage` or via the `SCHOLAR_FLUX_REDIS_USERNAME` and `SCHOLAR_FLUX_REDIS_PASSWORD` environment variables.
- **RedisStorage & MongoDBStorage Availability Checks**: The `RedisStorage.is_available()` and `MongoDBStorage.is_available()` methods now support usernames, passwords, and other rarely required connection fields via additional keyword parameters to account for scenarios where connection verification requires authentication. Additional configurations are only used for connection when explicitly passed via keyword parameters or when available via environment variables.
- **MongoDB Environment Database Selection (Potentially breaking)**: MongoDB configuration parameters, `db` and `collection`, were moved from the `MongoDBStorage.DEFAULT_CONFIG` dictionary (now `SettingsDict`) to dedicated class attributes, `MongoDBStorage.DEFAULT_DATABASE` and `MongoDBStorage.DEFAULT_COLLECTION`. This refactor differentiates these settings from dedicated `MongoClient` connection parameters and ensures that their defaults are migrated to a single point of access. In addition, the environment variables, `SCHOLAR_FLUX_MONGODB_DATABASE` and `SCHOLAR_FLUX_MONGODB_COLLECTION` were defined to provide a means of setting the database via environment variables when required for the response cache (optional). Note that Session Cache via `requests-cache` uses its own set of defaults that are unaffected by `db` and `collection` parameters.


### Added

**SearchAPI Initialization & Parameter Handling**:
- **API Auth Support**: The `BaseAPI` and `SearchAPI` implementations optionally allow for the direct assignment of an authorization subclass via the `auth=` keyword parameter on the following methods: `SearchAPI.prepare_search`, `SearchAPI.prepare_request`, `SearchAPI.make_request`, `SearchAPI.search`, `SearchAPI.build_auth`, `BaseAPI.prepare_request`, and `BaseAPI.send_request`. The `auth=` keyword parameter accepts `AuthAPIKeyNoOp`, `AuthAPIKeyHeader`, `AuthAPIKeyParameter`, or similar custom subclasses that inherit from `requests.auth.AuthBase`. When selected, API key/token selection and authentication are handled via a valid `AuthBase` subclass that encapsulates the authentication logic.
- **SearchAPI Parameter Updates (Potentially breaking)**: Modified core class constructors for the `SearchAPI`, defining parameters such as `request_delay`, `user_agent`, `timeout`, `use_cache`, `masker`, `rate_limiter` as keyword only, separating core configuration parameters from those that are primarily automatically configured based on the provider or user's environment, enhancing initialization and constructor readability at a glance. This applies to `SearchAPI.make_request`, `SearchAPI.prepare_search`, `SearchAPI.search`.
- **API Key Existence Checks**: `SearchAPI._api_key_exists` now checks whether an API key exists with a non-missing value instead of `True` when the key exists within the dictionary of specified parameters. While the previous behavior allowed for the conditional removal of API keys with Falsy values during request preparation, the same can now be accomplished via `auth=AuthAPIKeyNoOp()` to omit API keys on a per-search basis.
- **Prepare Request API Key Update & Deprecation (Potentially breaking)**: The updated `SearchAPI.prepare_request`, changes the `api_key` positional parameter into a keyword parameter and deprecates the parameter with removal expected in `v0.8.0`. This change seeks to standardize API key parameter handling via a standard interface that is primarily handled by the `SearchAPI.build_auth()` method. Ensure that API key, if needed for a particular provider (e.g., Springer Nature), is defined on the instantiation of the `SearchAPI`. Otherwise, the `auth=` keyword parameter can be set directly in cases where the API key needs to be overridden.
- **APIKeyValidationException**: A new `APIKeyValidationException` subclasses `APIParameterException` to indicate API key-related parameter errors that often occur during API initialization or search execution when an API key is required but has an invalid type. For easier debugging and tracing, the `RetryHandler` and `SearchCoordinator` now directly propagate `APIParameterException` and `APIKeyValidationException` to more easily indicate when search-related errors occur as a result of configuration settings.
- **API Parameter Build Update**: The `SearchAPI.build_parameters` method now includes an optional `include_api_key` parameter that controls whether an API key is added as a secret string to the prepared parameter dictionary or is omitted entirely. If include_api_key=None, an API key is only added when a provider is configured to include API keys in `params` as opposed to `headers`. Internally, `SearchAPI.search` explicitly uses `include_api_key=False` when an `auth=` parameter is directly provided by the user or another calling method that passes a non-missing `auth=` parameter. Otherwise, the addition of API keys in `headers` or `params` is dependent on the current API provider configuration.

**Multi-Page Record Retrieval**:
- **SearchResultList Record Accessibility**: The `SearchResultList` now introduces `normalized_records`, `data`, and `processed_records` properties to more closely align with existing functionality regarding cross-response normalization (`SearchResultList.normalize()`) and processed page accessibility (`SearchResultList.join()`). When each property is called, a flattened list of available processed or normalized records is returned, without the need to directly access and manipulate the underlying response to view available records. Similar to how the `SearchResult.processed_records` and `SearchResult.normalized_records` properties are implemented, the `SearchResultList.processed_records` and `SearchResultList.normalized_records` properties only append successfully retrieved/normalized records to a one-dimensional list, skipping results containing `ErrorResponse` and `NonResponse` types that contain no available records. Note that `SearchResultList.normalized_records` may return an empty list unless responses are normalized on retrieval (`coordinator.search_pages(range(1, 4), normalize_records=True)`) or afterward (`search_results.normalize()`).


### Changed

**Configuration & Package Settings**:
- **Unset Environment Configurations**: The `ConfigLoader` now optionally allows for the removal of settings loaded from the environment via the `ConfigLoader.unset` method. In addition to removing loaded or updated session-level configurations, this method optionally removes OS-level environment variables from the current session via `scholar_flux.config_settings.unset("[ENVIRONMENT_VARIABLE_HERE]", unset_os_env=True)`.
- **Guarded Secret ConfigLoader Expansion**: Updated `ConfigLoader._guard_secret` to automatically guard the `API-KEY`, `API_TOKEN`, and `API-TOKEN` patterns when configuration settings including these keywords are set. When an environment variable contains at least one pattern, its respective value is stored as a secret string to avoid accidental exposure in repr values when printing underlying configurations directly to the console. This update is directly relevant to `Crossref`, where header-based secrets are loaded via the `CROSSREF-PLUS-API-TOKEN` alias from the OS environment as a fallback when `CROSSREF_API_KEY` is empty.
- **Default ConfigLoader Secret Pattern Definition**: The `ConfigLoader._guard_secret` now uses the newly added `ConfigLoader.DEFAULT_SECRET_PATTERNS` class attribute with the aim of standardizing the location for match identification logic — enabling the expansion of guarded patterns without requiring `ConfigLoader` subclasses to handle special cases. The complete list of secret patterns also encompasses the patterns: `API[-_]TOKEN`, `API[-_]KEY`, `USERNAME`, `PASSWORD` (each case-insensitive, although caps are used for consistency).
- **Parameter Map Additions**: The `BaseAPIParameterMap` and `APIParameterMap` each introduce new `api_key_in_headers`, `api_key_scheme`, and `DEFAULT_API_KEY_PARAMETER` class variables, enabling provider-level control over the method used to transmit API keys during requests.
- **APIParameterConfig Updates**: Parameter configuration now features `APIParameterConfig.extract_api_key` and `APIParameterConfig.validate_api_key` methods for safe API key extraction with type validation. The previous `APIParameterConfig._get_api_key` method is now renamed to `._include_api_key` to more closely indicate its functionality in the preparation of parameter dictionaries with API keys extracted from disparately named fields and/or keyword arguments.
- **Crossref Configuration API Token Handling**: Crossref Plus API token authentication is now handled automatically via `AuthAPIKeyHeader`. Previously, header support for Crossref and other providers required manually updating the `SearchAPI.session.headers` dictionary to add the token and its value directly. Now, the `ProviderConfig` for Crossref appends `api_key_in_headers=True` and `api_key_scheme=Bearer` to indicate and enable header-based token authentication. When `SearchAPI.search()` is called, the API key is read via `CROSSREF_API_KEY` (falling back to `CROSSREF-PLUS-API-TOKEN` on setup) if it doesn't exist and subsequently temporarily injects the API token into the request header, only unmasking and appending the secret to the request header right before transmission via the `AuthAPIKeyHeader` class.
- **ConfigLoader Error Handling Updates**: The functionality of `ConfigLoader.__init__`, `ConfigLoader.load_config`, `ConfigLoader.save_config`, and `ConfigLoader.write_key` now support optional error raising via the `raise_on_error` keyword parameter. Each method uses `scholar_flux.utils.handle_exception()` to determine whether errors should be written to the logs (`raise_on_error=False`) or re-raised (`raise_on_error=True`) after logging. The addition of a `raise_on_error: bool | None = None` allows for backward compatibility regarding when errors are raised while allowing for more granular control of .env path selection.
- **ConfigLoader Key Export Updates (Potentially breaking)**: For consistency with the naming conventions, `ConfigLoader.write_key` parameters, `key_name` and `key_value`, were renamed to `key` and `value`, respectively. In addition, the `ConfigLoader.write_key` method now optionally writes current configuration settings to the environment without requiring end-users to directly specify the value that should be written. If an associated value isn't provided, a `KeyError` is either raised or logged depending on the value of the `raise_on_error` parameter. The parameters, `env_file` and `create`, were converted to keyword-only parameters with the aim of lessening the chance of accidental placement of potentially sensitive `value` fields in the `env_path` position.
- **ConfigLoader .env File Resolution**: Refactored `ConfigLoader.process_env_path` (formerly a private method) to raise an error by default when a path cannot be resolved. Previously, the private method, `ConfigLoader._process_env_path`, would simply fallback to the `ConfigLoader.DEFAULT_ENV_PATH` when an error occurred. The previous behavior is now opt-in — the default `.env` path will be returned when providing the keyword parameter, `raise_on_error=False` or `raise_on_error=None`.

**Session Cache Type Safety & Error Handling Improvements**:
- **Flexible Error Modes**: The `CachedSessionManager` now features three distinct error handling modes: (1) `True` - raises exceptions immediately, (2) `False` - logs warnings and defines fallbacks when encountering errors in component preparation/session initialization, and (3) `None` - delegates default error handling logic to each underlying method. As an example, while encryption serializer-related errors are raised by default, the selected cache backend will still default to `sqlite` when default backend environment variable resolution fails.

**EncryptionPipelineFactory Updates**:
- **Secret Key Preparation Renaming & Description**: Renamed the `EncryptionPipelineFactory._prepare_key` (private class method) to `EncryptionPipelineFactory.prepare_secret_key` (public class method) and updated the method docstring to indicate its utility for checking environment variable secret key availability. This class method efficiently retrieves the current secret key from the environment if saved, and can be used to verify whether default session encryption is enabled with a requisite secret key available through the OS environment.

### Fixed

**SearchAPI Prepare Search**: Updated the `SearchAPI.prepare_search` to guard against the edge case that an endpoint is used with a page to preview the API endpoint being queried (e.g., `endpoint="/v2/api"` → `endpoint="/v3/api"`).
**SearchAPI APIParameterConfigSetter**: Updated the `SearchAPI.parameter_config` property setter to enable the assignment of `BaseAPIParameterMap` and `APIParameterMap` subclasses. Although the `APIParameterConfig.as_config()` constructor enables instantiation from `BaseAPIParameterMap` and `APIParameterMap` instances, the `SearchAPI.parameter_config` property setter previously accepted `APIParameterConfig` instances only, raising an `APIParameterException` for all other types. While `APIParameterConfig` instances are the recommended method of assigning the `SearchAPI.parameter_config` property, this update ensures increased flexibility in `SearchAPI` parameter configuration/mapping assignment.

### Developer Notes:
- **Docstring Update**: Updated docstrings to reflect current functionality and class initialization parameters within the `api`, `security`, `utils`, `sessions`, and `data_storage` modules.
- **Test Reorganization**: Relocated tests for session creation and encryption from `tests/utils/` to `tests/sessions/` for module alignment and consistency with the directory structure of the source code.
- **SensitiveDataMasker Initialization Relocation**: Refactored the initialization location of the `SensitiveDataMasker` to the `scholar_flux.security.__init__` module. On package initialization, the refactored `initialize_package()` method now accepts and returns the `masker` as a passthrough when supplied as a keyword parameter (i.e., `initialize_package(masker=security.masker)`). This refactor enables the use of the package-level logger within the `config_loader` module, enabling easier masking of potentially sensitive fields.
- **Fallbacks and Exception Handling**: The `scholar_flux.utils.helpers` module now defines `with_fallback` and `handle_exception` utility functions for the further simplification of static typing and error handling patterns applied throughout the codebase. The `with_fallback` function enables the application of statically typed fallbacks when the variable received is `None`. This method uses overloads to constrain static typing to either the primary object's type, if available, or the static type of the default when the primary object is `None`. The `handle_exception` function simplifies the application of error handling patterns where a function may need to raise an error for special cases (`raise_on_error=True`) or gracefully continue otherwise (`raise_on_error=False`). These two methods are used extensively for loading environment configurations where initialization requires graceful error handling and the ability to distinguish between missing, empty, and invalid user-defined parameters.
- **Try-None Logic Update**: The `scholar_flux.utils.helpers.try_none` helper function now supports the conversion of empty secrets masked with `pydantic.SecretStr` to None. As a result, attempting to verify whether an API key read via the `ConfigLoader` will convert `PUBMED_API_KEY=''` and `SCHOLAR_FLUX_CACHE_SECRET_KEY="None"`, for example, from a secret string (when read and automatically guarded) to `None` when called (e.g., `try_none(config_settings.get("SCHOLAR_FLUX_CACHE_SECRET_KEY"))` → `None`).
- **Conditionally Loading .env Files**: To handle when .env files are resolved at a more granular level, the `scholar_flux.utils.initializer` now reads from the `SCHOLAR_FLUX_LOAD_ENV` variable to determine whether a `.env` file should be read and processed during package initialization. When a `.env` file has not been directly specified (which is the case during package initialization), the `SCHOLAR_FLUX_LOAD_ENV` is read and coerced into a boolean via `coerce_bool`, defaulting to `True` when coercion returns None instead. The `tests.testing_utilities.prepare_env` function sets this to `False` on initialization to ensure that separately configured `.env` files do not affect the test suite when otherwise globally configured by the user.
- **Mypy Dependency Update**: Updated the supported `mypy` version (`>=1.10,<2.0` → `^2.0.0`), pinning all versions from `2.x.x` as supported. The version update does not introduce any breaking changes or impacted validation logic to v0.6.0.
- **Dict/SettingsDict-Compatible Type Hints**: For compatibility with existing infrastructure, `mypy` (strict) type annotations use a `SettingsLike` TypeVar (for bounded return types) and `SettingsDictType` annotations for validation and type safety via `pydantic`. On assignment to `pydantic` models such as the `SearchAPIConfig` (`api_specific_parameters`) and `CachedSessionConfig` (`kwargs`), dictionaries and `SettingsDict` instances are equally compatible — dictionaries are automatically converted to `SettingsDict` instances under the hood within `pydantic` models to decrease exposure likelihood when verifying parameter dictionaries and settings via the console.
- **Overload Decorators**: Added `@overload` decorators to `CachedSessionManager.configure_session()` and `CachedSessionManager.with_session()` to provide precise return type hints based on the `raise_on_error` parameter. IDEs, consoles, and linters can expect that the `CachedSessionManager.with_session()` constructor will return a `CachedSession` or raise an error when `raise_on_error=True` is specified.
- **SearchAPI.make_request Parameter Rename**: `SearchAPI.make_request()` (internal method) now renames the `current_page` parameter to `page` to standardize the API across the codebase. This brings the signature in line with front-facing search methods (e.g., `SearchCoordinator.search_page`, `SearchAPI.search`, etc.), which require no changes to method calls.

### Security

**Package Dependencies**
- **Pytest Minimum Version Dependency Update**: Updated pytest minimum dependencies from v8.4.1 to v9.0.3. Although UNIX based systems protect against similar vulnerabilities by default, this update mitigates the (mainly theoretical) risk of DOS or privilege escalation regarding symlinked temporary directory writes to attacker-controlled directories on UNIX-based systems (`CVE-2025-71176`).

- **SearchResult Computed Field Decorators**: Updated the `SearchResult.cached` and `SearchResult.retrieval_timestamp` decorators to ensure that mypy identifies these as both computed fields and properties in downstream applications (such as MCP servers relying on response metadata) rather than callable functions.

Removed stray double whitespaces between text prose and trailing (invisible) whitespace after each line across the codebase and documentation.

## [0.5.1] - 04/28/2026
### Added
- **Session Cache Environment Variable Configuration**: For more granular session cache control, this version bump introduces support for the `SCHOLAR_FLUX_SESSION_CACHE_DIRECTORY` environment variable as an optional override for cached session persistence. When selecting a session cache directory via environment variables on `CachedSession` initialization, the cache directory is assigned in the following priority order: `SCHOLAR_FLUX_SESSION_CACHE_DIRECTORY` > `SCHOLAR_FLUX_CACHE_DIRECTORY` > `scholar_flux.package_metadata.get_default_writable_directory()`.

### Security

**Package Dependencies**
- **Requests Minimum Version Dependency Update**: Updated the `requests` library dependency to require version `2.33.0`. This prevents vulnerability CVE-2026-25645 `Insecure File Reuse` when extracting data from zip files.

The input parameters are exactly the same as the basic initialization of the `CachedSessionManager`, except for parameter order (`backend` is the only positional parameter, whereas all others are keyword parameters) and the fact that a `CachedSession` is initialized instead of a `CachedSessionManager`. To create a `CachedSession` with MongoDB with the default host and port, for example, use `CachedSessionManager.with_session(backend='mongodb', expire_after=86400, user_agent=...)`. - **Package Initialization and Logging Setup**: The `initialize_package` function now more gracefully accounts for potential errors and edge cases in log-level setup via the `SCHOLAR_FLUX_LOG_LEVEL` setting. The `verify_connection` keyword parameter also ensures that `CachedSession` instances using encryption and decryption for request cache serialization are using the correct secret key from session to session, failing fast in the session initialization step rather than later on when a request is actually sent using the `CachedSession`.

**Observability**:
- **Rate Limiting and Retry Handling Observability**: Due to the unpredictability of API request formats, timeout errors, etc., it's often necessary to know what went wrong when the unexpected occurs. The `RetryHandler` and `RateLimiter` both now include a class-level, thread-safe `HistoryDeque` that records rate limiting durations, timestamps, and response codes to help users more easily observe how request delays and rate limiter settings influence the time between requests to any specific API. After creating a `SearchCoordinator` and sending a request, retry-attempt history can be found at `coordinator.retry_handler.history` (or `RetryHandler.history`), and rate limiting metadata can be referenced from `coordinator.api.rate_limiter.history` (or `RateLimiter.history`). - **Excessive Delay Protection**: The `RetryHandler` now raises a `RetryAfterDelayExceededException` when a server's `Retry-After` header exceeds the `RetryHandler.max_backoff` limit and the class variable, `RetryHandler.RAISE_ON_DELAY_EXCEEDED=True`. This prevents long, indefinite waits and unexplained pauses due to silent rate limits. This alert is handled at the level of the `SearchCoordinator` that then returns an `ErrorResponse` to record the error type, error message, and exact response from the API. The log and error message alerts users to adjust their configuration and limit the rate of requests made in an interval (after respecting the minimum delay). This setting can be controlled via the `scholar_flux.api.RetryHandler.RAISE_ON_DELAY_EXCEEDED` class attribute (default: `True`). On the next user-initiated search, if the previous `Retry-After` header from the same API still indicates that a delay before the next request still remains, `ScholarFlux` will continue to respect this delay and log a message indicating the time that remains before the next request is sent.
- **History Deques for Request Monitoring**: The `scholar_flux.api.rate_limiting.history` module implements three classes created specifically for observability: the `HistoryDeque`, `RetryAttempt`, and `RateLimitEvent`. The `HistoryDeque` can store either `RetryAttempt` or `RateLimitEvent` dataclasses. This deque subclass operates as a class-level, thread-safe history, storing the last `n` (default=1000) retry attempts (for the `RetryHandler`) and rate limiting events (for the `RateLimiter` and `ThreadedRateLimiter`) while allowing transparent monitoring of outbound requests without the need to enable logging. For observability, the `HistoryDeque` implements the following methods: `create` (a factory method that creates a bounded `HistoryDeque`, storing the `HistoryDeque.DEFAULT_MAX_HISTORY` most recent entries (default=1000)), `export_history` (for converting the Deque into a list of dictionaries containing `RetryAttempt` or `RateLimitEvent` fields and masking sensitive parameters in the process), `modify_history_size` (for resizing `HistoryDeque.maxlen`), and `clear_history` (for removing all previously recorded entries).

- Updated the `MultiSearchCoordinator` to directly and always use the provider's recorded minimum request delay from the `threaded_rate_limiter_registry`.
- Updated the docstring of `MultiSearchCoordinator` to include a usage example and details on shared rate limiting.
- Updated the CLI representation of `RateLimiter` and `ThreadedRateLimiter` instances to display the class name and minimum interval for easier debugging.
- Modified the rate limiter to use `min_interval` as a property with a setter - this change ensures that `min_interval` is validated the moment it is set and raises an APIParameterException when encountering values other than `float`/`int`/`None`.
- Stashed a feature that would allow Class/Instance level control over unknown API-specific parameters in `APIParameterConfig`. Currently, unknown parameters are filtered by default for safety. This feature can be revisited if more flexible parameter handling is needed in the future.
